# Lesson Format

House style for every `lessons/*.html` in this workspace, **whatever the topic**.
Deryk asked for this on 2026-08-16; treat it as binding until they say otherwise.

The examples below are Rust, because that was the first topic. The rules are not: read
"compiles and runs" as "produces the observable outcome the stage promised", and
"compiler error" as "whatever the tool tells you when you get it wrong". A cooking
lesson has stages; a yoga lesson has stages; the reasoning is identical.

## The core rule

**Never show the finished work up front.**

A lesson builds it in numbered **stages**. Each stage adds a small, motivated
change, explains what that change does and *why it's needed*, and ends in a program that
compiles and runs. The finished file is what the reader has in front of them at the end —
it is never presented at the start as a thing to be reverse-engineered.

The reason: reading a complete forty-line file teaches recognition. Building it in six
steps, each of which visibly changes the result, teaches causation. You can only explain
a thing you watched become necessary.

## Stage anatomy

Every stage has four parts, in this order:

1. **Goal** — one sentence, phrased as an observable outcome. "A blank window appears."
   Not "add the App trait."
2. **The change** — only the lines being added or edited. Mark added lines with
   `<span class="add">`; show just enough surrounding code to locate them, dimmed with
   `<span class="dim">`. Never re-print the whole file.
3. **Why** — what each new construct does. This is the teaching. If a stage introduces
   two unrelated ideas, it is two stages.
4. **Run it** — the exact command, and what they should see. In a `<p class="run">`.

## Rules

- **Every stage must actually work, and you must prove it.** Run each intermediate
  stage before publishing — for code, that means compiling it (`cargo check` and
  friends); for anything else, the equivalent check. Do not reason about whether it
  works. A stage that doesn't strands a beginner with no way to tell whether they made
  the mistake or you did.
- **Verify the artifact, not your intent.** Extract the code back out of the rendered
  HTML and compile *that*. This has caught a line-count mismatch that reasoning about
  the source never would.
- **One new idea per stage.** Working memory is the binding constraint.
- **Prefer a stage that fails on purpose** where the failure teaches the next idea. Show
  the *real* output, copied verbatim from an actual run — never a paraphrase. Good tools
  explain themselves; let them do the work.
- **Deferred complexity gets named, not hidden.** When a stage includes boilerplate that
  can't be explained yet, say so explicitly and say which lesson will explain it. Silent
  hand-waving reads as "you're not meant to understand this."
- **Type it, don't paste it.** Say so in stage 1 of each lesson.
- **The full file appears once, at the end**, under "Where you ended up" — as a
  checkpoint to diff against, not as the teaching device.

## Every document is self-contained

Lessons and reference docs ship as **single HTML files** with all CSS and JS inlined —
open, move, mail, or print one anywhere and it still looks right. Nothing loads from
disk at runtime.

They are still authored from `assets/`, so the styling doesn't drift across lessons —
or across topics. Each document carries marked regions:

```html
<!-- @assets:style.css,quiz.css,quiz.js -->
  ...generated...
<!-- /@assets -->
```

`python3 build.py` regenerates whatever sits between those markers. It's idempotent, and
it never touches anything outside the markers. It finds documents at any depth, so a new
topic needs no build configuration.

Assets resolve **nearest-first**: from the document's own directory up to the workspace
root, the first `assets/<name>` wins. So a tutorial can ship a component only it needs
(a chess board, a pose diagram) by dropping it in its own `assets/`, and can override a
shared component by reusing its filename. Put something in the root `assets/` only when
a second topic would plausibly want it.

**Workflow:** edit `assets/style.css`, run `python3 build.py`, done. Editing the
generated `<style>` block inside an HTML file works until the next build, then gets
silently overwritten — so don't. A new lesson just needs the marker pair in its
`<head>`; the build fills it in.

## Components available in `assets/`

Use these rather than inventing markup. Add to them when a lesson needs something new
and reusable.

| Markup | Renders as |
| --- | --- |
| `<section class="stage">` | One numbered stage; the number is generated by CSS, so stages renumber themselves when you reorder them |
| `<p class="goal">` | The stage's observable outcome |
| `<p class="run">` | The "run it" block — command plus what they should see |
| `<p class="filename">` + `<pre>` | A file tab welded to the top of the code block. Must be immediately adjacent |
| `<span class="add">` / `<span class="dim">` | New lines / dimmed context inside a `<pre>` |
| `<pre class="error">` | Compiler output. Auto-labelled and red-bordered so it never reads as code to type |
| `<details class="recall">` | Free-recall prompt — answer before revealing |
| `<div class="quiz">` | Multiple choice with shuffled options and instant feedback (`quiz.js`) |
| `<div class="callout key/warn">` | Emphasis / a caveat |
| `<div class="callout note">` | **Filled highlight** for a must-do detail that's easy to skim past. Goes *before* the code block, never after |
| `<p class="sidenote">` | Margin note; collapses inline below 1180px |
| `<div class="thesis">` | The one sentence the lesson exists to deliver |

Two code treatments exist and they mean different things: **inline `<code>`** is a warm
bordered chip on the paper, so identifiers stay scannable mid-sentence, while **`<pre>`**
is a dark panel — something you run, not something you read. Never nest a chip inside an
already-monospaced context; the stylesheet strips it automatically inside `pre`, `.run`,
`.filename`, and quiz options.

Every block colour is a CSS variable (`--code-*`, `--tok-*`, `--err-*`), and
`@media print` redefines that whole set to a light theme — dark blocks are a toner sink
on paper and the syntax colours muddy. **Never hardcode a colour inside a `pre` rule**,
or it will survive into print and break the flip.

**A stage has exactly one `<h3>`.** The stage number is generated from it, so a second
`<h3>` inside the same `<section class="stage">` renders a duplicate "Stage N" label.
Subsections within a stage are `<h4>`. (The stylesheet now scopes the label to
`:first-of-type` so the damage is contained, but the markup should still be right.)

**One code block, one edit site.** If a stage touches two places in the file, that is two
blocks with their own file tab, location hint, and sentence of prose — never one block
with a `… and elsewhere:` comment in the middle. The second edit in such a block reliably
gets skimmed past, because the reader's attention is spent on the first. When a stage
needs several, say so up front ("this stage takes three separate edits"), number them in
the prose, and warn if the file won't compile until all of them are in.

**Abridged checkpoints are split, not commented.** A checkpoint that elides unchanged
code must never do it with a `// … unchanged …` line inside the listing — a reader
skimming code reads that as something to type, and it hides how much is missing. Instead:
break the listing into separate `<pre>` pieces, each with its own file tab and location
hint, and put a `<div class="callout note">` between them naming exactly what sits in the
gap and roughly how long it is. Where the gap falls *inside* a function body, so splitting
is impossible, mark it with `<span class="gap">` — a centred, ruled-off marker that cannot
be mistaken for code.

**Abridged checkpoints are never numbered.** Line numbers on a complete file are stable
and useful; on a fragment they run 1..N and quietly disagree with the reader's real file.
Only a full-file checkpoint gets `<pre class="numbered">`.

**A `.run` block is a command and its output — nothing else.** Every line in one is
read as "type this" or "see this". So an *action* tucked into a `<span class="note">` at
the bottom reads as more output and gets skipped. If the reader must do something —
delete a scratch file, undo a `chmod`, make a directory — it goes in its own run block or
a `<div class="callout note">` that says what breaks if they don't. Real case: lesson 5
ended a run block with "Then: rm editor/notes.md", which was a prerequisite for the next
stage; skipping it made the fix look broken. `build.py` warns on commands found inside
run-block notes.

**If you announce a count, it must be right.** "Three edits" means exactly three code
blocks in that stage. A reader tallies the edits as they go and stops when they reach the
number — so under-counting silently leaves their file wrong, and the *next* lesson's diff
then fails to apply against it. This is not hypothetical: lesson 3 claimed four edits and
had five, the status label never got added, and lesson 4's replacement had nothing to
match. `python3 build.py` now audits every stage and warns on a mismatch. Never let a
single ordinal ("Fourth — …") introduce two blocks.

**Show every edit, including token-level ones.** If a stage changes something *inside* a
line the reader already has — a renamed parameter, a dropped underscore — the green
`.add` band alone will not register it, because the whole line looks new. Pair it with a
`.del` of the old line and a `<div class="callout note">` above the block naming the
exact compiler error they'll hit if they miss it. This was a real failure in lesson 1
(the `_ui` → `ui` rename), and it is the single most likely way a stage silently breaks
for a beginner.

If a whole file is new (a "replace everything with this" stage), do **not** wrap it in
`.add`. Green means "these lines, among the ones you already have" — tinting everything
tells the reader nothing.

## Everything else still applies

- Short. One tangible win. Tied to the tutorial's own `MISSION.md`.
- Built from `./assets/` components; new reusable pieces go there, never inlined.
- Retrieval-practice quizzes near the end, using `assets/quiz.js`. Equal word counts
  across options.
- One primary source recommended for further reading.
- A reminder that the agent is their teacher and questions are welcome.
- Anchor links to related lessons and `reference/` docs.
- **Every self-test explanation links back to where the idea was taught** — inside the
  reveal, not beside the question, so it doesn't short-circuit the recall attempt.
  Anchor the specific paragraph or table, not the top of a stage.
